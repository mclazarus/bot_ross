# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Bot Ross is a Discord bot that generates images using OpenAI image models. It has five main commands: `&paint` (gpt-image-2 by default), `&dpaint` (always dall-e-3), `&meme` (GPT generates a meme prompt, then paints it), `&remix` (uses attached image(s), the image(s) of a message the command replies to, and/or the image(s) of a Discord message link pasted in the prompt — same server only — as input to the OpenAI image-edit endpoint, falling back to `&paint` behavior when no image is found; see Message Links), and `&release_image` (deterministically derives a mad-libs image prompt from a git hash or any text — see Release Image). Every one of those except `&meme` (plus the hidden `&xpaint`/quality-variant `&hpaint`/`&mpaint`/`&lpaint`) accepts `|` to chain up to five image steps in one command, each step editing the previous step's output (see Pipes). It also has magic-management commands: `&magic_list`, `&magic_show`, `&magic_add`, `&magic_update`, `&magic_remove`, and `&magic_rate` (see Magic Paint); and macro-management commands: `&macro_list`, `&macro_show`, `&macro_add`, `&macro_update`, and `&macro_remove` (see Macros). It also runs a background daily-image scheduler — a deterministic "image of the day" each morning plus themed edits of that same image through the day (see Daily Image of the Day) — when `DAILY_IMAGE_CHANNEL_ID` is configured, plus daily-schedule-management commands `&daily_list`, `&daily_show`, `&daily_add`, `&daily_update`, `&daily_remove`, and `&daily_toggle`; and one further command that *runs* a slot rather than managing the schedule: `&daily_image`, a manual stand-in for the morning generate slot, since there is no catch-up for a slot missed while the bot was down (see Daily Image of the Day). It tracks monthly usage with a configurable limit and persists stats to `data/request_data.json`.

## Running

```bash
# Copy env.example to .env and fill in your secrets
cp env.example .env

# Run directly
pip install -r requirements.txt
export $(grep -v '^#' .env | xargs)
python bot_ross.py

# Run with Docker
./build.sh
./run.sh .env /path/to/data
```

Environment variables (see `env.example`):

| Variable | Default | Description |
|---|---|---|
| `OPENAI_API_KEY` | required | OpenAI API key |
| `DISCORD_BOT_TOKEN` | required | Discord bot token |
| `API_LIMIT` | `100` | Max image generations per calendar month. The shipped daily-image schedule (see Daily Image of the Day) alone fires 4 slots/day — 1 `generate` + 3 `edit` — so 4 × ~30 days ≈ 120 generations/month minimum (more on a base-image recovery or a retry), which by itself exceeds this default. An operator who sets `DAILY_IMAGE_CHANNEL_ID` and leaves `API_LIMIT` at its default hits the monthly cap partway through the month, after which `over_limit()` refuses every command — daily-scheduled and user-triggered alike — for the rest of the month; raise `API_LIMIT` accordingly when enabling the scheduler |
| `IMAGE_MODEL` | `gpt-image-2` | Image model for `&paint` and `&meme` |
| `IMAGE_MODERATION` | `low` | Content moderation level for gpt-image-2 (`low` or `auto`) |
| `MEME_MODEL` | `gpt-5.4-mini` | GPT model used to generate meme prompts |
| `MAGIC_PAINT_RATE` | `0.05` | Starting chance (0.0-1.0) that `&paint`/`&remix` silently appends a background gag to the prompt; invalid or out-of-range values are coerced to the default. Read once at startup — the live rate is then controlled in-process via `&magic_rate` and is **not** persisted (resets to this value on restart) |
| `BOT_TIMEZONE` | `America/New_York` | IANA timezone the daily-image schedule's slot times are wall-clock in (the container itself runs UTC). An unknown/invalid name falls back to UTC with a logged warning rather than crashing at import — see Daily Image of the Day |
| `DAILY_IMAGE_CHANNEL_ID` | unset | Discord channel id the daily image/edits post to. Unset (the default) disables the scheduler entirely; also accepts a pasted `<#channel_id>` mention. Setting this adds ~120 generations/month against `API_LIMIT` (see above) — raise `API_LIMIT` to match, or the bot runs out of budget partway through the month |
| `DAILY_IMAGE_ENABLED` | `true` | Set `false` to disable the daily-image scheduler outright, independent of whether a channel id is configured |

## Architecture

The bot lives in `bot_ross.py` (discord.py, `commands.Bot`, command prefix `&`), with seven companion modules holding pure, side-effect-free logic so they can be unit tested without importing the bot: `release_image.py` for `&release_image` (see Release Image), `magic_paint.py` for the magic-mixin rate calculation (see Magic Paint), `macros.py` for `;macro` expansion (see Macros) — the latter two delegate their shared library load/save/seed logic to `json_library.py` — `image_size.py` for `&remix`'s aspect-ratio-aware edit sizing and (as of the `--res`/orientation-flag feature) `&paint`'s family's generation sizing (see below), `daily_schedule.py` for the daily-image scheduler's DST-safe time resolution, schedule validation, and retention pruning (see Daily Image of the Day), `pipe_chain.py` for `|` chain splitting and status-message formatting (see Pipes), and `message_links.py` for `&remix`'s Discord-message-link parsing/classification/capping (see Message Links). Images are fetched directly via `aiohttp` to the OpenAI REST API (not the SDK), returned as base64, and sent as Discord file attachments. Generation POSTs JSON to `/v1/images/generations` (`fetch_image`), by default at the model config's fixed `1024x1024` size, but `&paint`/`&hpaint`/`&mpaint`/`&lpaint`/`&xpaint` can override it via `--square`/`--landscape`/`--portrait`/`--res WxH` (see below); `&dpaint`/`&meme`/`&release_image` are unaffected by the sizing feature. `&remix` with an image instead POSTs multipart form data to `/v1/images/edits` (`fetch_image_edit`), which has no `revised_prompt` field; it forwards the model config's `quality` and `moderation` (when supported) so the edit matches the chosen quality tier, and returns PNG b64 like generation. Unlike generation, the edit `size` is not the model config's default: `&remix` reads `width`/`height` off the first resolved `discord.Attachment` and calls `image_size.resolve_edit_size(...)`, whose no-flag default coerces those dimensions (via `coerce_generation_size`) to match the input image's own size/aspect as closely as a valid size allows — gpt-image-2's edit endpoint honors arbitrary sizes, so the output keeps the input's shape rather than being bucketed. `auto` is used whenever Discord didn't report usable dimensions (a non-image attachment slipped through, or an image Discord couldn't probe). The chosen size is forwarded through `do_the_art`'s `size` parameter into `fetch_image_edit`, which sends it in place of the config default; it is logged (a size-selection line in `&remix`, plus the resolved size on the edit-success line) but never announced in the channel. The `get_meme_prompt()` function uses the older `openai.ChatCompletion.create` sync API (v0.27.x) to generate meme prompts.

`image_size.py` also owns the generation-side sizing for `&paint`/`&hpaint`/`&mpaint`/`&lpaint`/`&xpaint`: `parse_size_flags` strips `--square`/`--landscape`/`--portrait`/`--res WxH` out of the prompt before macro expansion or magic paint ever see it, and `coerce_generation_size` deterministically coerces an arbitrary `--res` into a size the `/v1/images/generations` endpoint accepts (multiple of 16, aspect ratio in `[1/3, 3]`, within a `3840x2160` box, and at least `GEN_MIN_PIXELS` total area — the endpoint's "minimum pixel budget", determined empirically to be ~655,360 px and floored to the smallest confirmed-accepted area, 665,856 = 816×816; sub-budget sizes are scaled up preserving aspect, with a rounding-safe guard so the floor survives the ÷16 rounding). Empirically gpt-image-2's `/v1/images/edits` endpoint honors arbitrary sizes too (despite the docs only listing the three standard sizes + `auto`), so `resolve_edit_size` coerces every path with the **same** `coerce_generation_size` as the generation path rather than snapping to a standard size — an explicit `--res`, and the no-flag default (which coerces the first attachment's own `width`/`height` to match it as closely as possible, or `auto` when Discord didn't report them). The only difference from `resolve_generation_size` is that default: paint defaults to a square, remix to the input image's own size. `resolve_generation_size`/`resolve_edit_size` each return `(size, requested)`, and callers post a coercion notice only when `requested` is set and differs from `size` — an orientation preset, an already-valid `--res`, or the no-flag default (which leaves `requested` unset) stays silent. `fetch_image` (generation) and `fetch_image_edit` (edit) both now accept a `size` override, copying `MODEL_CONFIGS[...]["params"]` before applying it so the shared config dict is never mutated. `&dpaint` (dall-e-3 has a different size/model set), `&meme`, and `&release_image` are **not** wired up to any of this; adding dall-e-3 sizing later would mean giving it its own size profile alongside `GEN_*`/`ORIENTATIONS`, since dall-e-3's allowed sizes differ from gpt-image-2's. `image_size.py` also has a small standalone piece used only by the daily scheduler: `png_dimensions(data)` parses a PNG's `(width, height)` straight out of its 24-byte IHDR header (`struct.unpack`, no Pillow dependency) — returns `None` (never raises) on anything that isn't a well-formed PNG, so a scheduled edit can fall back to `AUTO` exactly like `resolve_edit_size` does when Discord reports no dimensions.

State is stored in `data/request_data.json` — monthly request counts (keyed by `YYYY-MM`), total meme count (`memes`), safety violation count (`safety_trips`), total magic-applied count (`magic`), total successful-remix count (`remixes`), total successful-release-image count (`release_images`), total successful-daily-generate count (`daily_images`) and total successful-daily-edit count (`daily_edits`), total macro-expansion count (`macros`) and total macro-miss count (`macro_misses`), total fully-completed `|` pipe chain count (`pipes`) and total successfully-completed chain segment count including segment 1 (`pipe_segments`, see Pipes), and `magic_rate_history` (the last 10 rate changes, each `{"user", "rate", "time"}`, newest last). The `data/` volume also holds the working magic library (`data/magic_prompts.json`, seeded at startup — see Magic Paint), the working macro library (`data/macros.json`, seeded at startup — see Macros), the working daily-image schedule (`data/daily_schedule.json`, seeded at startup — see Daily Image of the Day), the daily scheduler's own fired-slot bookkeeping (`data/daily_state.json`, its own file, never a key inside `request_data.json`, so per-minute scheduler writes can't race `save_data`'s command-triggered read-modify-write), and the retained daily base images (`data/daily_images/`). The `over_limit()` function gates image generation against `API_LIMIT` — including daily-scheduler generations, which count against the same monthly limit like every other image command. Note that `data/` is a runtime-only Docker volume mount (see `run.sh`) — it is not part of the repo or image, so it must never be used to ship static content (the magic library, macro library, and daily-schedule working copies are seeded there at runtime from the image, not shipped).

**`get_current_month()` is timezone-aware, not a UTC-only helper.** It returns `datetime.now(BOT_ZONE).strftime("%Y-%m")` (`BOT_ZONE` is the parsed `ZoneInfo` for `BOT_TIMEZONE`, see Daily Image of the Day) rather than the container's own UTC clock. This is a **deliberate behavior change to the monthly spend limit**: the `API_LIMIT` month boundary now rolls over at local midnight in `BOT_TIMEZONE`, which can be up to ~5 hours earlier or later than the old UTC-midnight boundary, once a month. `over_limit()`, `&stats`, and every per-month counter key all read through `get_current_month()`, so this one change moves all of them together. `start_time` (used for `&stats`' uptime) and `_record_rate_change`'s timestamp intentionally still use the system-local `datetime.now()`/`datetime.now().astimezone()` — this change is scoped to the spend-limit boundary only.

**Graceful shutdown / draining.** discord.py installs no SIGTERM handler, so as PID 1 in Docker the bot would otherwise ignore `docker stop` until it SIGKILLs, hard-killing in-flight generations. `on_ready` installs loop signal handlers (SIGTERM from `docker stop`, SIGINT from Ctrl+C) that call `_graceful_shutdown`: it sets the `draining` flag (a global `@bot.check`, `_reject_while_draining`, then refuses new commands with a note), waits up to `DRAIN_TIMEOUT` seconds (env, default **300** — raised from 60 in the Pipes commit, since `_piped` now brackets a whole multi-segment `|` chain, up to 5 sequential image calls, as one drain unit) for `active_requests` to reach 0, then `await bot.close()` (so `bot.run()` returns and the process exits). `active_requests` is a module counter incremented/decremented around the whole body of `do_the_art` — the single chokepoint every image command awaits — so all in-flight work is what's drained (`&meme`'s quick pre-`do_the_art` `get_meme_prompt` step is not tracked); a pipe chain additionally wraps its own outer `active_requests` increment around the entire `_run_chain` call (see Pipes), so the drain loop never sees a false-zero gap between two segments of the same chain. `run.sh` stops with `docker stop -t $STOP_TIMEOUT` (default **330**, must exceed `DRAIN_TIMEOUT`) so Docker's force-kill can't preempt the drain. A minimal `on_command_error` swallows the drain `CheckFailure` and `CommandNotFound` to keep logs clean.

## Magic Paint

The pure logic — the rate roll, mixin selection/application, library load/save/seed, and the `parse_magic_rate`/`format_magic_rate`/`slugify_magic_id` helpers — lives in **`magic_paint.py`** (no Discord/OpenAI/bot side effects; every function takes its path/rate/library explicitly rather than reading a bot_ross global). `bot_ross.py` keeps thin wrappers (`_load_magic_library`, `_save_magic_library`, `_apply_random_magic_entry`, `maybe_apply_magic_paint`, `_seed_magic_library`) that bind those pure functions to `MAGIC_PROMPTS_FILE`/`DEFAULT_MAGIC_PROMPTS_FILE` and the live `MAGIC_PAINT_RATE`; `parse_magic_rate`/`format_magic_rate` are imported directly. `test_magic_paint.py` (stdlib `unittest`, run `python -m unittest test_magic_paint`) imports `magic_paint` directly and covers the headline rate promise (at 25% over 100 generations ~25 get a mixin, plus large-sample convergence), rate parse/format round-trips, mixin application/fail-open, slugging, library I/O, and seed-library data integrity (exactly one Costanza entry, unique ids). Note the startup env parse of `MAGIC_PAINT_RATE` (a plain float in `[0.0, 1.0]`) is intentionally distinct from `parse_magic_rate` (the `%`/fraction-aware parser used by `&magic_rate`) and stays inline in `bot_ross.py`.

The magic library is a list of joke prompt-additions: recurring background characters (asbestos-hunting cats, a lightning-eyed rice-hat engineer, a capybara, a cycling anteater, a farmer hedgehog and his quail wife) plus exactly one non-subtle "...but it's George Costanza." entry.

There are two copies. The **seed** — `magic_prompts.json` at the repo root (tracked in git, shipped in the Docker image as `DEFAULT_MAGIC_PROMPTS_FILE`) — is the read-only default. The **working copy** lives on the persistent volume at `data/magic_prompts.json` (`MAGIC_PROMPTS_FILE`); this is what `&magic_add`/`&magic_remove` mutate and what `_load_magic_library()` reads fresh on every trigger (never cached). At startup `_seed_magic_library()` copies the seed onto the volume only if the working copy is absent, so user-added mixins survive image rebuilds/redeploys. This is the one deliberate exception to "never use `data/` to ship static content": nothing is shipped there — it's seeded at runtime from the image. `magic_paint.py`'s `load_magic_library`/`save_magic_library`/`seed_magic_library` are thin delegates onto the shared `json_library.py` (also used by `macros.py` — see Macros).

Each library entry has an `id` and `text`; entries added at runtime also carry `author` and `added` (ISO date), and entries edited via `&magic_update` also carry `editor` and `edited` (ISO date) — the original `author`/`added` are left untouched by an edit. Original built-in entries omit all four fields, and all read paths tolerate their absence (shown as `built-in`/`—`, or omitted entirely for `editor`/`edited`). The library is written back via `_save_magic_library()` with `indent=2, ensure_ascii=False` (preserves unicode like `♥️`/`—`).

`maybe_apply_magic_paint(prompt)` rolls against `MAGIC_PAINT_RATE` and only touches disk if the roll succeeds; `_apply_random_magic_entry(prompt)` does the guaranteed (100%) load-pick-append used directly by the hidden `&xpaint` command and by `&remix` when an image is attached with no text. Whenever magic paint triggers (roll or guaranteed), the bot's initial quote message gets a `🖌️` appended as a tell — the actual appended text is never shown to the user. The `magic` counter is incremented in `send_quote()` (the single chokepoint every magic path calls) when the tell is shown, so it counts at reveal time regardless of whether generation then succeeds. `&xpaint` is a hidden (`hidden=True`, excluded from `&help`) always-on variant of `&paint`, kept undocumented in the README by design.

**Magic-management commands** (all open to everyone, matching the rest of the bot — no permission checks):
- `&magic_list` — renders a lightweight index of the library (id + author per entry, no prompt text), chunked under Discord's 2000-char limit via `send_long()`, led by a hint line pointing at `&magic_show <id>` (to read a mixin's prompt) and `&magic_update <id> <text>` (to change it).
- `&magic_show <id>` — shows an entry's untruncated text plus author/added (and editor/edited, if present).
- `&magic_add <text>` — appends an entry with an auto-generated slug id (`_slugify_magic_id`, first ~4 words, `-2`/`-3`… on collision), `author=ctx.author.name`, `added=today`.
- `&magic_update <id> <text>` — replaces an existing entry's `text` in place (id/author/added untouched), setting `editor=ctx.author.name` and `edited=today`. Unlike `&magic_remove` + `&magic_add`, this doesn't churn the id or lose creation history.
- `&magic_remove <id>` — drops the entry with that id (or reports it wasn't found).
- `&magic_rate [value]` — no arg reports the live rate as a percent plus who last changed it; with a value, `parse_magic_rate` interprets it (trailing `%` = exact percent, e.g. `.1%`→0.001; no `%` and `>=1` = percent number, e.g. `10`→0.10; no `%` and `<1` = raw fraction, e.g. `.1`→0.10, `.001`→0.001), clamps to `[0.0, 1.0]`, reassigns the `MAGIC_PAINT_RATE` module global, and records the change via `_record_rate_change` (persisted to `magic_rate_history`, last 10). Note the live rate itself is in-memory only, so after a restart it resets to env/default while `magic_rate_history` (and thus `&stats`' "Last rate change") persists — the two can legitimately disagree. `_record_rate_change` stores a timezone-aware timestamp (`datetime.now().astimezone().isoformat()`); `format_rate_change_time()` renders it as `YYYY-MM-DD HH:MM:SS ±HHMM` wherever it's displayed (`&magic_rate`, `&stats`), falling back to no offset for legacy naive timestamps recorded before this was tracked.

## Macros

`;token` anywhere in a `&paint`/`&hpaint`/`&mpaint`/`&lpaint`/`&dpaint`/`&xpaint`/`&remix` prompt is expanded, in place, to a short library snippet before the prompt reaches magic paint or the image API — e.g. `&paint A ;rhe is trapped in a datacenter` (see `&macro_list` for the id table). `&release_image` and `&meme` are deliberately **not** wired up to macro expansion.

The pure logic — the `;token` regex, lookup/substitution, id normalization/validation, and library load/save/seed — lives in **`macros.py`** (no Discord/OpenAI/bot side effects; mirrors `magic_paint.py`'s shape). `bot_ross.py` keeps thin wrappers (`_load_macro_library`, `_save_macro_library`, `_seed_macro_library`) binding those functions to `MACROS_FILE`/`DEFAULT_MACROS_FILE`, plus `expand_prompt_macros(ctx, prompt)` — the single chokepoint every prompt-bearing command calls, always as the **first** step (before `maybe_apply_magic_paint`/`_apply_random_magic_entry`), so an expanded macro's text is itself eligible to receive a magic mixin appended after it. `test_macros.py` (stdlib `unittest`, run `python -m unittest test_macros`) mirrors `test_magic_paint.py`'s coverage style: expansion correctness (single/multiple/repeated/case-insensitive/no-recursion/fail-open), id parse/validate, library I/O, and seed-data integrity.

Expansion is a **single pass** over the original prompt: replacement text is never rescanned for further `;tokens`, so a macro whose text happens to contain `;something` cannot recurse or chain. There is no escape syntax — a bare `;` followed by a space or punctuation is ordinary prose and is left alone; `;;token` still expands `token` (the leading `;` is untouched prose, the second `;` triggers the match). Lookup is case-insensitive against normalized ids (`normalize_macro_id`: lowercased, leading `;` and surrounding whitespace stripped).

Whenever any `;token` is present, `expand_prompt_macros` echoes the fully expanded prompt back on an `expanded prompt: ...` line (via `send_long`, so long prompts chunk safely). Crucially this is the **post-macro, pre-magic-paint** prompt — macro expansion always runs first — so it shows the requester exactly what their macros became while still **never revealing a magic mixin** (magic is appended afterward, and stays hidden behind the `🖌️` tell as before). Unlike magic paint, macros are an explicit, deliberate tool the requester typed, so echoing the expansion is transparency, not a spoiler. An unresolved token is swapped for a joke placeholder from `FALLBACK_EXPANSIONS`, a **static code constant** (deliberately not stored in `macros.json`, so it can't be edited via `&macro_add`/`&macro_update`), and called out on a leading `🎲` line naming every miss (e.g. `` 🎲 `;foo`, `;bar` (macro not found, good luck) ``) above the `expanded prompt:` line, so the requester knows a macro didn't resolve, without blocking generation. `expand_prompt_macros` increments the persisted `macros`/`macro_misses` counters (shown in `&stats`) by however many tokens actually hit/missed on that call — 0 if the prompt had no `;tokens` at all, in which case nothing is written to disk and no message is sent.

There are two copies, the same two-copy seed/working-volume model as the magic library: the **seed** — `macros.json` at the repo root (tracked in git, shipped in the image as `DEFAULT_MACROS_FILE`) — is the read-only default; the **working copy** lives on the persistent volume at `data/macros.json` (`MACROS_FILE`), mutated by `&macro_add`/`&macro_update`/`&macro_remove` and read fresh on every expansion (never cached). `_seed_macro_library()` copies the seed onto the volume at startup only if the working copy is absent.

Each library entry has an `id` (the bare token — no leading `;`) and `text`; entries added at runtime also carry `author`/`added` (ISO date), and edited entries also carry `editor`/`edited` (ISO date) — the same shape as the magic library. Unlike `&magic_add` (which auto-slugs an id from the mixin text), `&macro_add <id> <text>` takes the id **explicitly**, since it's also the literal string a user types as `;<id>` in a prompt.

The `text` of a seed entry (and of every `FALLBACK_EXPANSIONS` member) is by convention an **article-less** noun phrase ending in a comma: the writer supplies the article in the prompt (`A ;rhe is trapped...`), so an expansion beginning with "a"/"an"/"the" would render "A a caucasian engineer...". `test_macros.py` asserts this over both the seed library and the fallbacks. It's a convention for the shipped data only — nothing rejects a user-added macro that breaks it.

**Macro-management commands** (all open to everyone, matching the rest of the bot — no permission checks): `&macro_list` (id + truncated text + author index, chunked via `send_long()`), `&macro_show <id>` (untruncated text + author/added/editor/edited), `&macro_add <id> <text>` (validates the id via `is_valid_macro_id`, refuses duplicates and points at `&macro_update`, stores `author=ctx.author.name`, `added=today`), `&macro_update <id> <text>` (replaces `text` in place; id/author/added untouched; sets `editor`/`edited`), and `&macro_remove <id>` (drops it, or reports it wasn't found) — the same shape as the magic-management commands, minus a rate: macro expansion is deterministic (driven by the presence of a `;token`), not probabilistic, so there is no `&macro_rate` equivalent.

## Release Image

`&release_image <git-hash-or-text> [--george] [--vN]` mints a repeatable avatar for a software release. The input (a git hash, or any text — it may contain spaces) is hashed to deterministically pick a mad-libs-style image **prompt**, so the same input always yields the same prompt. The generated image isn't deterministic (OpenAI generation isn't), but the prompt is — that's what makes a release's avatar stable. The command is **deliberately not subject to magic paint** (no `maybe_apply_magic_paint`/`_apply_random_magic_entry` calls; `send_quote(ctx)` is called with `magic=False`). On success it increments a `release_images` counter (in `do_the_art` alongside `remixes`), shown in `&stats`. The resolved prompt, short seed, and algorithm version are revealed in the channel.

All pure logic lives in **`release_image.py`** (no Discord/OpenAI/bot side effects, so `test_release_image.py` imports it directly — importing `bot_ross` isn't possible under test because module load ends in `bot.run()`):
- `parse_release_args(args)` → `(source, version, georgify)`. Flags are stripped and the rest is rejoined as `source`: `--george`/`--costanza` set georgify; `--version N`, `--version=N`, and `--vN` set the version.
- `build_release_prompt(source, version=None, georgify=False)` → `(prompt, seed, version_used)`. Picks one phrase per category via `_release_index`, applies `georgify_template` to the subject when georgify is on (`"George Costanza if he were {subject}"`), then `template.format(**picks)`. Raises `KeyError` on unknown version (the command catches it and lists available versions).
- `_release_index(source, version, category, n)` = `int.from_bytes(sha256(f"{source.strip()}|{version}|{category}").digest()[:8], "big") % n`. Uses SHA-256 (not Python's `random`) for cross-platform/interpreter stability, and hashes each category with its own name so categories are **independent** — editing one word list, or adding/reordering categories, won't shift another category's pick. The public seed shown to users is `sha256(source.strip())[:8]`.

**Versioned artifact.** The templates + word lists live in **`release_algorithms.json`** at the repo root (`RELEASE_ALGORITHMS_FILE`, resolved relative to `release_image.py`, loaded once at import). It's a JSON object keyed by version string; each version has `template`, `georgify_template`, `categories` (the fixed fill-in order), and `word_lists` (category → phrase list). Because the prompt is a pure function of `(input, algorithm)`, **any** change to a template or word list changes the space of outputs, so such a change must ship as a **new version** while old versions are retained (folding `version` into the hash key means the same input picks differently per version). Unlike the magic library, this file is **static, read-only content**: it ships in the Docker image (`COPY release_algorithms.json .`) and is read straight from the image — it is **never** seeded onto the `data/` volume. To add a version: add a new top-level key (e.g. `"2"`) with its own template/lists; `&release_image --v2` targets it and the default is the highest numeric key.

`test_release_image.py` (stdlib `unittest`, run `python -m unittest test_release_image`) covers determinism, uniqueness/reproducibility across 500 inputs, category variety, structural validity (no leftover `{placeholders}`, every pick present), georgify, versioning, arg parsing, and data integrity (per-category minimum counts — subject/setting ≥ 100, others ≥ 24 — no duplicates, template placeholders map to categories).

## Pipes

`|` lets a single command run up to five image steps in one invocation — e.g. `&paint a lighthouse | make it winter | now at night` — across `&paint`/`&hpaint`/`&mpaint`/`&lpaint`/`&dpaint`/`&xpaint`/`&remix`/`&release_image` (every image command except `&meme`, which is deliberately not wired up). The first segment behaves exactly like the command does today, magic mode and all; every later segment is an image-edit of the *previous* segment's output, posted as a **reply to the first image** (a fixed anchor, not the previous one), so the chain is traversable backward from any link.

The pure splitting/formatting logic lives in **`pipe_chain.py`** (no Discord/OpenAI/bot side effects — imports at most `typing`):
- `MAX_SEGMENTS = 5` (4 pipes) and `TOO_MANY_MESSAGE = "Okay, simmer down, buddy."` — exact, load-bearing string.
- `split_pipeline(raw, max_segments=MAX_SEGMENTS)` → `(segments, dropped, error)`. No `|` at all ⇒ `([raw], 0, None)` with `raw` returned **verbatim, unstripped** — the single most important compatibility guarantee, since it's what keeps every non-piped invocation byte-for-byte identical to before this feature existed. Otherwise `raw.split("|")`'s length is checked against `max_segments` **before** any empty segment is dropped — `"a | | | | | b"` is five pipes (six raw parts) and must get `"too_many"`, not a quiet reduction to `["a", "b"]`; this ordering is the module's single most important behavior (see `test_pipe_chain.py`'s case 9). Below the cap, each part is stripped at both ends only (internal whitespace preserved) and empty results are dropped and counted in `dropped`; nothing surviving is `"empty"`.
- `chain_stopped_message(step, total)`, `chain_complete_message(total)`, `dropped_note(dropped)` — the fixed status-line templates, pure string formatting.
- `class ArtResult(NamedTuple)` — see Model Abstraction; defined here rather than in `bot_ross.py` so its always-truthy guarantee is unit-tested.

There is deliberately **no escape syntax** for a literal `|` in a prompt — the same documented stance `macros.py` takes on `;`. The module is named `pipe_chain.py`, not `pipes.py`, specifically to avoid shadowing the stdlib `pipes` module — `coloredlogs`' `converter` submodule imports and uses stdlib `pipes.quote`, and `WORKDIR /app` in Docker puts a same-named local module first on `sys.path`.

**`bot_ross.py` wiring** (thin, untested — mirrors the daily scheduler's "logic lives in the pure module, glue lives here" split):
- Each of the eight piped commands' body was extracted verbatim into a `_*_once(ctx, text, …)` helper — `_paint_once` (shared by `&paint`/`&hpaint`/`&mpaint`/`&lpaint`/`&xpaint`, parameterized by `request_type`/`model`/`magic_mode`), `_dpaint_once`, `_remix_once` (its `raw` argument may be `None` — an image-only remix with no text), `_release_image_once`. `magic_mode` is `"roll"` (`&paint`/`&remix`'s existing probabilistic `maybe_apply_magic_paint`), `"none"` (`&hpaint`/`&mpaint`/`&lpaint`/`&dpaint`/`&release_image` — release images stay magic-free on every chain step, not just segment 1), or `"always"` (`&xpaint`'s existing guaranteed `_apply_random_magic_entry`).
- Every command body is now one or two lines calling `_piped(ctx, raw, first_runner, request_type, model, magic_mode)`, which does the splitting **before** size flags, macros, or magic paint ever see the text (splitting after macro expansion would let a library macro whose text happens to contain `|` inject extra pipeline steps). `raw is None` (only possible for `&remix`) skips splitting entirely and runs `first_runner` once. A `"too_many"` split error sends `TOO_MANY_MESSAGE` and **only** that message; `"empty"` sends a fixed all-empty line; a nonzero `dropped` sends `dropped_note(dropped)` first. A single surviving segment (the overwhelming majority of invocations — no `|` at all) runs `first_runner` once, exactly the pre-Pipes code path. A real (≥2 segment) chain brackets the **whole run** with the module `active_requests` counter before calling `_run_chain`, so a shutdown drain waits for every segment rather than seeing a false-zero gap between two segments of the same chain (this is why `DRAIN_TIMEOUT` was raised — see Graceful shutdown / draining above).
- `_run_chain(ctx, segments, first_runner, request_type, model, magic_mode)` runs segment 1 via `first_runner`, then each later segment via `_pipe_edit_once`; a falsy result at step N sends `chain_stopped_message(N, total)` and stops (prior images stay posted, no `pipes` increment). Every segment that *does* complete — including segment 1 — bumps the persisted `pipe_segments` counter via `_bump_stat('pipe_segments')`; a fully-completed chain additionally bumps `pipes` and posts `chain_complete_message(total)`. `_bump_stat(key, amount=1)` is a small generic load/increment/save helper (`_bump_magic_counter` — see Magic Paint — is now a thin call onto it).
- `_pipe_edit_once(ctx, raw, prev_bytes, anchor, model, magic_mode)` is every non-first segment: parse size flags → strip → macro-expand (skipped for a flags-only segment, which falls back to the same `"creatively reinterpret this image"` literal `&remix` uses for an image with no text) → apply magic per `magic_mode`. Sizing reads the **previous segment's own PNG output** via `image_size.png_dimensions(prev_bytes)` fed into `resolve_edit_size` (falling back to `AUTO` on unparseable bytes) — deliberately **not** the first segment's originally-*requested* size, since a first-segment `&remix` that resolved to `AUTO` has no size to thread forward, but the output PNG's own header always does. It then calls `do_the_art(ctx, prompt, "pipe", model, images=[(prev_bytes, "image/png")], size=size, reply_to=anchor, content=("🖌️" if magic else None), quiet=True)` — `request_type="pipe"` deliberately doesn't match any of `do_the_art`'s `remixes`/`release_images`/`daily_image`/`daily_edit` counters, so only segment 1 ever earns those; a `&dpaint` chain's edit segments silently fall back to `gpt-image-2` via the existing `get_edit_model`, since dall-e-3 has no edit endpoint. On a truthy result with `magic` set, `_bump_magic_counter()` is called **after** the send succeeds — the 🖌️ content IS the reveal on a quiet segment (there's no quote message to attach a tell to), so counting has to wait for it to actually exist.
- `&stats` gained two lines (`Pipe chains: {n}` / `Pipe segments: {n}`) and each piped command's `help=` string gained the sentence `Chain follow-up edits with | (up to 5 steps).`.

`test_pipe_chain.py` (stdlib `unittest`, run `python -m unittest test_pipe_chain`) covers `split_pipeline`'s full contract (no-pipe verbatim passthrough, the too-many-before-empty-dropping precedence case, boundary/custom-`max_segments` cases, non-str `TypeError`, purity), the fixed message templates, and `ArtResult`'s always-truthy/field-order contract.

## Message Links

`&remix` resolves Discord message links pasted anywhere in its prompt (e.g. `https://discord.com/channels/<guild>/<channel>/<message>`, the `<>`-wrapped no-embed form, `ptb.`/`canary.`/`www.` client subdomains, `discordapp.com`) into that message's image attachments. Resolution order, and the reason for it: own command attachments → reply-target attachments → linked-message attachments, appended **last** — so a directly attached image (or a replied-to one) stays `attachments[0]` and keeps driving the edit size, and a pasted link can never silently change the output size of a remix whose real subject was the user's own image. Links are stripped out of the prompt text (see `strip_message_links`) **before** size-flag parsing, macro expansion, or magic paint ever see it, so a URL never ends up echoed in an `expanded prompt:` line or sent to the image model as prose. All link fetching completes before `send_quote`, so the requester isn't left staring at a quote mid-fetch. Up to 4 unique links (`message_links.MAX_LINKS`) are resolved per invocation; duplicates collapse into one before the cap is applied.

**Security is the entire point of this feature's design**, stated exactly because it's easy to get backwards: the guild id embedded in a pasted URL is attacker-controlled text typed by whoever pasted the link — nothing stops someone from putting the *current* server's guild id in a link that actually points at a channel in a *different* server, since Discord routes a message by its channel id, not by whatever guild id happens to sit in the URL next to it. `message_links.classify_link` (pure, in `message_links.py`) only compares those URL-derived ids against `ctx.guild.id` — it is a cheap pre-filter that keeps obviously-foreign links from reaching a network call, and it is explicitly **not** the security boundary; its own docstring says so. The actual authorization lives in `bot_ross.py`'s `_resolve_linked_images` and runs against the **resolved objects**, never the URL: (a) the resolved channel's `guild.id` equals the invoking `ctx.guild.id`, re-derived from the fetched `discord.abc.GuildChannel`/`Thread` object, and (b) the **invoking user** — `ctx.author`, never the bot — has both `view_channel` and `read_message_history` on that resolved channel, checked via `channel.permissions_for(ctx.author)`. Check (b) is the one that matters most: the bot's own permissions are often broader than a given requester's, so skipping it would let anyone paste a link into a channel they personally cannot see and have the bot fetch its image for them anyway — an image-exfiltration hole. Every per-link failure (unresolvable channel, either authoritative check failing, an unfetchable message, or an unexpected exception) is bucketed into one combined notice and logged with its real reason; **the channel is deliberately never told which check failed** — "channel not found" vs. "bot lacks access" vs. "you lack permission" vs. "message deleted" all render identically, so `&remix` can't be used as an oracle to enumerate which private channels or messages exist. A message with no image attachments (same `content_type` predicate `&remix` already uses for its own attachments) gets its own separate notice, as does hitting the 4-link cap or the 4-image-across-kept-links cap.

`test_message_links.py` (stdlib `unittest`, run `python -m unittest test_message_links`) joins the local test gate; it covers `MESSAGE_LINK_RE`'s host-matching edge cases (canonical/`discordapp`/`ptb`/`canary`/`www` hosts, the `<>` wrapper, tolerated trailing slash/query string, punctuation never swallowed into an id, and — the sharpest security cases — that a lookalike host like `notdiscord.com` and a suffix-attack host like `discord.com.evil.com` never match), `strip_message_links`'s verbatim-no-link passthrough and newline-preserving whitespace collapse, `classify_link`'s `ok`/`dm`/`no_guild`/`cross_guild` precedence (including the DM-takes-precedence-over-no_guild case and 19-digit-snowflake exact integer comparison), and `limit_links`' dedupe-then-cap contract (dedupe key is the full id triple, first occurrence wins, purity).

## Daily Image of the Day

An autonomous background scheduler — no Discord command triggers it — posts a deterministic "image of the day" every morning to a configured channel, then posts themed *edits* of that same retained image at fixed times through the day (lunch, quitting time, bedtime by default). All slot times are wall-clock in a single global `BOT_TIMEZONE` (default `America/New_York`), while the container itself runs UTC — DST gaps/folds and UTC/local day confusion are the dominant risk this feature has to get right, so essentially all of its logic is pure and exhaustively unit tested (`test_daily_schedule.py`).

**`daily_schedule.py`** (pure — no Discord/OpenAI/bot side effects, no module-level I/O, no function ever calls `datetime.now()` — "now" is always a parameter) owns:
- `parse_bool`/`parse_channel_id`/`get_zone` — lenient env-var parsing that never raises; `get_zone(name, fallback="UTC")` returns `(ZoneInfo, error_or_None)` so `bot_ross.py` can log its own warning on a bad `BOT_TIMEZONE` while this module stays log-agnostic.
- `load_schedule`/`save_schedule`/`seed_schedule` — thin delegates onto the shared `json_library.py` (same two-copy seed/working-volume pattern as the magic and macro libraries).
- `validate_schedule(entries)` → `(good_entries, errors)` — the same fails-open, per-entry tolerance `macros.py` established: one hand-corrupted schedule entry is dropped and reported, never crashes the scheduler. Also validates the optional `enabled` field (see below): present-but-non-bool is a rejection, exactly like the existing `magic` rule; absent is fine. **Duplicate ids are detected on the *normalized* id** (`normalize_slot_id`: stripped + lowercased), not the merely-stripped one, because that's what every lookup uses — the `&daily_*` commands resolve a typed id via `normalize_slot_id` and match it with `slot_entry_id`, which lowercases too. Comparing case-sensitively here let a schedule holding both `lunch` and `LUNCH` keep **both**, and since a command's lookup normalizes to `lunch` and stops at the first match, the `LUNCH` entry fired every day while being unreachable by `&daily_show`/`&daily_update`/`&daily_toggle`/`&daily_remove` alike — a slot you could watch posting but couldn't turn off. The invariant now enforced (and tested directly): anything surviving validation is addressable by a command. `format_schedule_lines` applies the same normalized-duplicate check, so `&daily_list` flags a shadowed row as `⚠️ ... duplicate id — it never fires` instead of rendering it as a healthy `(magic off, enabled)` summary.
- `slot_is_enabled(entry)` → `entry.get("enabled", True) is not False`. **Absent means enabled** — the entire backward-compatibility contract for the `enabled` field (see below); every reader of "should this slot fire" goes through this one function.
- `slot_instant(day, hour, minute, zone)` — the DST heart. Builds the wall-clock `datetime` with `fold=0` and normalizes it **through UTC** (`.astimezone(UTC).astimezone(zone)`), so a nonexistent (spring-forward gap) time is pushed forward by the size of the gap, and an ambiguous (fall-back fold) time resolves to its **first** occurrence — never a naive, silently-wrong wall-clock computation.
- `due_slots(now, entries, state, zone)` → `[(entry, day)]` — the scheduler's core query. `now` must be aware (a naive `now` raises `ValueError` immediately — treating it as local time would silently shift every slot by the zone's offset, the exact bug this module exists to prevent); a slot is due iff `0 <= now - slot_instant(...) <= MISS_WINDOW` (10 minutes), it hasn't already fired for that local day per `state`, **and** `slot_is_enabled(entry)` — a disabled slot is skipped before either candidate day is even considered. Both today's and yesterday's local date are checked as candidate days (a late-evening slot evaluated just after local midnight belongs to yesterday's day key). There is deliberately **no catch-up** beyond `MISS_WINDOW` — this alone (even with state lost/reset) prevents a fall-back-fold slot from double-firing, since the second occurrence of an ambiguous time is a full UTC-offset-delta past the first's normalized instant. Results are sorted by ascending instant (ties keep `entries`' order) so a `generate` slot always resolves before an `edit` slot due in the same tick.
- `mark_fired(state, slot_id, day)` — returns a new dict, never mutates.
- `seconds_to_next_minute(now)` — clamped to `[1.0, 60.0]`, used to phase-lock the scheduler's tick to the wall-clock minute boundary.
- `seed_source_for(day)`/`format_announcement_date(day)`/`render_message(template, day)` — `seed_source_for` feeds `release_image.build_release_prompt` (so the daily prompt is deterministic per local day, same algorithm `&release_image` uses for a git hash); `format_announcement_date` renders from literal `WEEKDAYS`/`MONTHS` tuples (never `strftime("%A"/"%B")`, which is locale-dependent); `render_message` substitutes `{date}` via `str.replace` (never `str.format`, so a hand-edited message with a stray `{`/`}` can't raise every day at slot time).
- `daily_image_filename`/`parse_daily_image_date`/`select_images_to_prune(names, keep=DAILY_IMAGE_RETENTION)` — retention. Filenames are `daily_image_YYYY_MM_DD.png`, strictly parsed (case-sensitive, zero-padded, calendar-valid) so only files this bot provably wrote are ever pruning candidates; pruning selects by **parsed date**, deduplicated by date first (so a corrupted duplicate directory listing can't skew which dates count toward `keep`), never by lexical filename order.
- `load_state`/`save_state` — the fired-slot bookkeeping is its own tiny `{slot_id: "YYYY-MM-DD"}` dict format (NOT `json_library`, which is list-of-entries-shaped). Fails open to `{}` on any corrupt shape; worst case is one slot re-firing once inside its 10-minute window, never a wedged scheduler.
- **`&daily_*` command-surface helpers** (backing the management commands below; mirrors `macros.py`/`magic_paint.py`'s division of labor): `normalize_slot_id`/`is_valid_slot_id`/`slot_entry_id`/`find_slot` (id handling, the last two mirroring `macros.entry_id`/a by-reference lookup that stays addressable even on a broken row); `format_slot_time` (canonical zero-padded `HH:MM`, so the file can't accumulate mixed formats); `validate_slot(entry)` (single-entry validation via `validate_schedule([entry])` — the one source of truth every write is checked against); `build_slot_entry(...)` (constructs a new entry for `&daily_add`, stricter than `validate_schedule` about a stray `edit_prompt` on a `generate` slot); `apply_slot_update(entry, field, value, ...)` (one-field-at-a-time, pure, returns a new dict — backs `&daily_update`); `toggle_slot(entry, ...)` (flips `enabled`, absent counts as enabled so the first toggle disables); `parse_flag_value`/`format_flag` (a **strict** true/false parser distinct from the lenient env-var `parse_bool` — a command typo like `magic ture` must raise, not silently fall back); `parse_add_fields(rest)` (splits `&daily_add`'s free-text tail on `FIELD_SEPARATOR` — see below); `format_slot_summary`/`format_slot_detail`/`format_schedule_lines` (render one/one/every entry for `&daily_list`/`&daily_show`); `truncate_text(text, limit=60)` (the shared 60-char-plus-ellipsis rule `format_slot_summary`'s message preview uses, and that `&daily_update`'s reply also uses to avoid echoing an unbounded `message`/`edit_prompt` value back through a bare `ctx.send` — Discord's 2000-char cap would otherwise make the *confirmation* silently fail to send on a long enough value, even though the write had already succeeded); `has_enabled_generate_slot(entries)` (gates the "no generate slot left" warning on `&daily_remove`/`&daily_toggle`/`&daily_update`); `schedule_file_is_corrupt(path)` (true iff `path` exists, is non-empty, but isn't valid JSON/isn't a list — distinguishes a hand-broken `data/daily_schedule.json` from a genuinely empty one, both of which `load_schedule` fails open to `[]` for; used by `&daily_list`/`&daily_add` so a syntax error doesn't read as "empty, add away" and get silently overwritten by the next `&daily_add`).

`test_daily_schedule.py` (stdlib `unittest`, run `python -m unittest test_daily_schedule`) is the heaviest test file in the repo: DST gap/fold resolution across four zones (`America/New_York`, `Europe/London`, `Asia/Kolkata` — no DST at all — `Australia/Sydney` — Southern-Hemisphere transitions on the opposite months), UTC-container-vs-local-day edge cases in both directions, the fall-back single-fire guarantee proven three separate ways, retention pruning (exact/over/under the keep count, cross-year ordering, duplicate/non-matching-name defense, shuffle-order independence), schedule/state I/O fails-open behavior, and — for the `&daily_*` command surface — the `enabled` schema's backward compatibility (a schedule/seed written before the field existed behaves identically; a disabled slot never fires, proven from six angles including a midnight-straddle case), every command-surface pure function's argument grammar (the ` :: ` add-field separator, the field-setter update grammar, the write invariant that a valid slot can never be made invalid by a command), and a round-trip class that writes/reloads a tempdir schedule to prove `enabled` persists as a real JSON boolean and the repo-root seed is never touched.

**`test_bot_ross_source.py`** (stdlib `unittest`, run `python -m unittest test_bot_ross_source`) is the one deliberate exception to "everything testable lives in a pure module": `bot_ross.py` can never be imported under test, but `do_the_art`'s `quiet=True` promise that the prompt (which may carry a hidden magic mixin) never leaks via the Discord attachment's filename or alt-text description is small, security/privacy-sensitive, and has no natural pure-module home. This file parses `bot_ross.py` with `ast` (never executes it) and asserts that shape structurally. Because it inspects `do_the_art`'s source shape rather than its pure-module behavior, it is intentionally tolerant of the ternary-vs-if/else-statement refactor a benign cleanup might make — treat any further tightening the same way (assert the security property, not incidental syntax). `DailyCommandsValidateBeforeSaveTest` uses the same `ast`-only technique for a second bot_ross.py-only property: `&daily_add`/`&daily_update`/`&daily_toggle` must call `daily_schedule.validate_slot(...)` before their `_save_daily_schedule(...)` call (by source line number), and every mutating `&daily_*` command must have no `await` between its `_load_daily_schedule()`/`_save_daily_schedule(...)` calls (a `ctx.send` in between would let two concurrent edits interleave on the single-threaded event loop and lose one). It **must be included** in the local test gate alongside the other modules: `python -m unittest test_daily_schedule test_bot_ross_source test_pipe_chain test_message_links test_image_size test_macros test_magic_paint test_release_image`.

**`bot_ross.py` wiring** (deliberately thin and untested — the loop itself can't be imported under test since the module ends in `bot.run()`; everything testable lives in `daily_schedule.py`):
- Config: `BOT_TIMEZONE`/`BOT_ZONE` (with a `logger.warning` if `get_zone` reports a problem), `DAILY_IMAGE_ENABLED`, `DAILY_IMAGE_CHANNEL_ID` — see the env var table above. Paths: `DAILY_SCHEDULE_FILE`/`DEFAULT_DAILY_SCHEDULE_FILE` (`data/daily_schedule.json` / `daily_schedule.json`, seeded via `_seed_daily_schedule()` at module bottom), `DAILY_STATE_FILE` (`data/daily_state.json`), `DAILY_IMAGES_DIR` (`data/daily_images/`, `os.makedirs(exist_ok=True)` at startup since a bind-mounted `data/` masks the Dockerfile's `mkdir`).
- `_ChannelContext` — a minimal `ctx` stand-in (`.send` delegating to a `discord.abc.Messageable`, `.author.name == "daily_schedule"`) so the scheduler can call `do_the_art` unchanged and inherit `over_limit`, the monthly counter, safety-trip accounting, and the `active_requests` drain bracket for free. Verified sufficient because `do_the_art` only ever touches `ctx.send`/`ctx.author.name`.
- `_daily_scheduler_loop()` is started idempotently from `on_ready` (guarded the same way `_signals_installed` guards the signal handlers, since `on_ready` refires on reconnect), held in the `_daily_task` module global with a `_log_daily_task_result` done-callback (a bare `create_task()` return value can be GC'd mid-flight, and a crashed loop would otherwise die silently). Each tick sleeps to the next minute boundary via `seconds_to_next_minute` (recomputed from the wall clock every iteration — self-corrects after an NTP step or host suspend within a minute), then runs `_run_due_daily_slots()` inside its own `try/except` (`CancelledError` re-raises; anything else is logged and the loop keeps going) — one bad tick must never kill the heartbeat.
- `_run_due_daily_slots()` loads+validates the schedule fresh every tick (never cached, matching the magic/macro libraries), warns on validation errors only when the error set **changes** (a `_last_schedule_errors` module global) so a persistently bad entry doesn't spam a warning every 60 seconds, resolves the channel (`bot.get_channel` falling back to `await bot.fetch_channel`, catching `discord.HTTPException`/`NotFound`/`Forbidden`) — **without marking anything fired** if that fails, so a transient Discord hiccup doesn't permanently burn the slot's `MISS_WINDOW` — then for each due slot **persists fired-state before running it** (a crash mid-generation must not re-fire on restart) and checks `draining` between slots.
- `_run_daily_slot(channel, entry, day)`: a `generate` entry builds the day's prompt via `release_image.build_release_prompt(daily_schedule.seed_source_for(day))` (logged, **never posted** — only the announcement + image are ever visible in the channel), optionally rolls magic (`entry["magic"]`, via the existing `maybe_apply_magic_paint`, tell appended to the announcement + `_bump_magic_counter()` — extracted out of `send_quote` specifically so the scheduler, which has no quote message, still counts scheduled magic), posts the announcement, then calls `do_the_art(..., "daily_image", ..., quiet=True)` with one retry (`_do_the_art_with_retry`, a 2-minute `asyncio.sleep` gated by `draining` before **and** after) before giving up and posting the fixed failure line. On success the retained PNG is written to `data/daily_images/` and pruned via `select_images_to_prune`. An `edit` entry reads today's retained base, silently regenerating it first (same retry pattern, no announcement, no magic roll — base recovery is plumbing) if missing, sizes the edit off the base's **own** dimensions (`image_size.png_dimensions` → `coerce_generation_size`, falling back to `AUTO` — mirrors `resolve_edit_size`'s no-flag default), then edits with one retry using the **same already-rolled** prompt (no second magic roll, no second announcement).
- New counters `daily_images`/`daily_edits` (incremented inside `do_the_art` per `request_type`), surfaced in `&stats` as `Daily images: {n}` / `Daily edits: {n}`.

**`data/daily_schedule.json` schema** (list of entries, same shape convention as the magic/macro libraries): `id` (unique, non-empty), `time` (`"HH:MM"` 24-hour wall time in `BOT_ZONE`), `type` (`"generate"` or `"edit"`), `message` (posted verbatim except `{date}` substitution), `edit_prompt` (required for `type: "edit"`), `magic` (optional bool, default `False` — `True` means the existing probabilistic roll, **not** always-on), `enabled` (optional bool, default `True` — `False` means the slot stays in the schedule but `due_slots` skips it, for every candidate day). **Absent `enabled` means enabled** — this default is what keeps every schedule file written before this field existed, including the shipped seed (which has no `enabled` key on any entry), scheduling exactly as it always has; `enabled` present but not a real bool (e.g. the string `"false"`, a classic hand-edit mistake) is rejected by `validate_schedule`, same as a non-bool `magic`, so the failure direction is always "the slot doesn't fire," never "it fires anyway." The shipped seed has four entries: `morning` (07:00, generate, `magic: false`), `lunch` (12:00, edit, `magic: true`), `quitting_time` (17:00, edit, `magic: true`), `goodnight` (22:00, edit, `magic: true`). The working copy is edited either by hand or via the `&daily_*` commands below (both write the same `data/daily_schedule.json`) — same working-copy/seed pattern as everything else; the repo-root seed is read-only and is never written by a command.

**Daily-schedule-management commands** (all open to everyone, matching the rest of the bot — no permission checks; same shape as `&macro_*`/`&magic_*` above). The `_run_due_daily_slots()` tick reloads the schedule fresh via `load_schedule` on every pass (never cached), so any of these commands' edits take effect within at most `~60s`, no restart required:
- `&daily_list` — one line per raw row of the file, in **file order** (not sorted by time — `due_slots` already sorts by instant, so list order carries no runtime meaning; this deliberately mirrors what a hand-editor sees). A row that fails validation is still shown, marked `⚠️` with the reason, so a broken entry never silently vanishes from the listing; a row with no usable id at all is called out separately since no command can address it. Appends a note when the scheduler can't run at all (`DAILY_IMAGE_ENABLED` false, or no `DAILY_IMAGE_CHANNEL_ID` configured) — so curating a schedule that can never post doesn't happen silently. If the schedule reads as empty AND `schedule_file_is_corrupt(DAILY_SCHEDULE_FILE)` is true, the reply says the file exists but couldn't be parsed rather than claiming it's genuinely empty — `load_schedule` fails open to `[]` on a syntax error the same way it does for a missing/empty file, and the two must not be conflated.
- `&daily_show <id>` — untruncated detail: time/type, message, edit prompt (shown whenever `type == "edit"` **or** a stray prompt is present on a `generate` slot), magic/enabled flags, and author/added/editor/edited provenance.
- `&daily_add <id> <HH:MM> <generate|edit> <message>` — for an `edit` slot, append `` :: <edit prompt>`` after the message. The separator is deliberately **`` :: `` (with a space on both sides), never `|`** — `|` is the pipe-chain operator elsewhere in the bot, and is legal literal text inside a message or edit prompt. An unspaced `::` (`a::b`, `a ::b`, `a:: b`, a trailing `a ::`) is a hard error rather than being silently folded into the message text. New slots are created with `magic: false` and `enabled: true`; there are deliberately no add-time flags for those — set them afterward with `&daily_update <id> magic on` / `&daily_toggle <id>`. Records `author`/`added`. Refuses to add (same `schedule_file_is_corrupt` check as `&daily_list`) when the working file exists but doesn't parse as JSON — appending to the fail-open `[]` in that case would silently overwrite every existing slot with a file containing only the one new entry.
- `&daily_update <id> <field> <value>` — changes exactly **one** field per invocation (fields: `time`, `type`, `message`, `edit_prompt`, `magic`, `enabled`); `value` is the entire rest of the line, so a message or edit prompt containing `|`, `;`, `::`, or `--` is stored verbatim — no quoting, no escaping. This is the direct answer to "change the time / the channel message / the edit prompt." The **write invariant**: a slot that's currently valid can never be made invalid by an update (refused, with the reason); a slot that's currently invalid can always be edited (otherwise a row broken in two fields could never be repaired), saved even if it's still invalid afterward, with a `⚠️ Heads up: ... still won't fire` note appended. The slot's `id` itself cannot be changed this way (remove and re-add under the new id instead) — renaming in place would orphan its `data/daily_state.json` fired-state key (keyed by id + local day) and risk a same-day double-fire under the new id. Records `editor`/`edited`. The reply never echoes a raw `message`/`edit_prompt` value — it's routed through `truncate_text` (same 60-char rule as `&daily_list`'s preview) and points at `&daily_show <id>` for the untruncated text, since Discord's 2000-char message cap can otherwise turn a long update into a write with no visible confirmation. Updating `enabled` to `off` appends the same "no enabled `generate` slot left" warning `&daily_remove`/`&daily_toggle` do (`NO_ENABLED_GENERATE_WARNING`, one shared constant across all three call sites) when it leaves none enabled — `&daily_update <id> enabled off` is a documented equivalent spelling of `&daily_toggle <id>` and must carry the identical warning.
- `&daily_remove <id>` — deletes the slot. Appends a warning if the schedule is now empty, or if no **enabled** `generate` slot remains (an `edit` slot would then silently repaint the day's base image on its own the first time it runs). The slot's key in `data/daily_state.json` is deliberately left behind (harmless — a stale key is never read for a different id, and if the id is re-added the same day it safely suppresses a duplicate post).
- `&daily_toggle <id>` — flips `enabled` (absent counts as enabled, so the first toggle disables); no `on`/`off` argument, since `&daily_update <id> enabled off` already covers explicit setting. Same "no enabled generate slot left" warning as `&daily_remove` when toggling the last one off. Works even on an already-broken row (a slot must always be switchable off regardless of what else is wrong with it).

Every write goes through `daily_schedule.validate_slot` before being saved (`build_slot_entry`'s own field checks for `&daily_add`; the write invariant above for `&daily_update`; trivially satisfied for `&daily_toggle`, since flipping a bool can't invalidate an otherwise-valid entry) — a typo can reject a write with an explanation, but it can never brick the scheduler. `find_slot` (used for lookup by every command) is deliberately validation-agnostic, so a broken row stays addressable/fixable/removable by id rather than becoming invisible to every command except hand-editing the file.

**`&daily_image`** is the one command that *runs* a slot rather than managing the schedule (the `&daily_*` commands above manage it). It exists because there is no catch-up: a morning slot missed while the bot was down is gone for good. The command does a due `generate` slot's work on demand, with two deliberate differences from `_run_daily_slot`'s generate path: it posts to the **invoking channel** (not `DAILY_IMAGE_CHANNEL_ID`), so it still works with the scheduler disabled entirely; and if today's base PNG is already retained it **reposts it verbatim** — no API call, nothing counted against `API_LIMIT`, no second magic roll (the retained PNG already baked in whatever the first roll decided), tagged `♻️ (repost — already painted today)`. Everything else matches the scheduled path: same deterministic prompt, same logged-never-posted rule, same `_do_the_art_with_retry`/`FAILURE_MESSAGE` handling, same `_save_daily_image` retain-and-prune. On a **successful** generate only, it calls `mark_fired` for the generate slot's id so a manual run at 06:58 can't be followed by a scheduled duplicate at 07:00; a failed generate deliberately leaves the slot unburned. It reads the slot's `message`/`magic` from the schedule via the pure `daily_schedule.find_generate_entry(entries)` (validates first, first-accepted-generate wins, `None` if the schedule has no valid generate entry — in which case the command falls back to its own `"It's the image of the day for {date}"` wording rather than `KeyError`-ing). `find_generate_entry` deliberately ignores `enabled` — it will happily hand back a **disabled** generate slot's wording, because `&daily_image` is user-initiated and already works with the scheduler off entirely; `enabled` only ever gates the automatic scheduler (`due_slots`), never this manual command. The repost-never-regenerates promise is guarded by `DailyImageRepostDoesNotRegenerateTest` in `test_bot_ross_source.py`, an AST-level check that no generation/magic call appears inside the `if png_bytes is not None:` branch and that the branch returns — one deleted `return` would otherwise silently turn every repost into a paid regeneration.

## Model Abstraction

`MODEL_CONFIGS` (defined near the top of `bot_ross.py`) captures per-model API differences:

```python
MODEL_CONFIGS = {
    "gpt-image-2": {
        "params": {"size": "1024x1024", "quality": "high"},
        "has_revised_prompt": False,   # Image API doesn't return revised_prompt
        "supports_moderation": True,
        "supports_edit": True,         # can be used with /v1/images/edits (&remix)
    },
    "dall-e-3": {
        "params": {"size": "1024x1024", "quality": "hd", "style": "vivid"},
        "has_revised_prompt": True,
        "supports_moderation": False,
        "supports_edit": False,        # dall-e-3 has no edits endpoint support
    },
}
```

`fetch_image(prompt, model, size=None)` looks up the config, builds the payload, and returns `{"image": b64, "revised_prompt": str_or_None}`; a non-`None` `size` overrides the config's default generation size, always via a fresh `dict(config["params"])` copy so `MODEL_CONFIGS` itself is never mutated. `do_the_art(ctx, prompt, request_type, model, images=None, size=None, reply_to=None, content=None, quiet=False)` calls `fetch_image` normally, or `fetch_image_edit` when `images` is provided (routed through `get_edit_model(model)`, which falls back to `gpt-image-2` if the requested model doesn't support edits), and skips the "Revised prompt" Discord message when `revised_prompt` is None. `size` (see `image_size.py`) is forwarded on both paths — to `fetch_image_edit` (in place of the model config's default edit size, for `&remix` and pipe-chain edit segments) and to `fetch_image` (in place of the model config's default generation size, for `&paint`/`&hpaint`/`&mpaint`/`&lpaint`/`&xpaint`); `&dpaint`/`&meme`/`&release_image` never pass it, so they keep each model config's fixed default.

**`reply_to`/`content` (added for Pipes)**: `reply_to`, a `discord.Message` or `None`, threads the posted image as a Discord reply via `reference=reply_to` — used so every pipe-chain segment past the first replies to the chain's first image (a fixed anchor), keeping the chain traversable backward from any link. If that send raises `discord.HTTPException` **and `reply_to` was not `None`** (a deleted anchor message resolves as Discord 400 `reference_unknown`), `do_the_art` retries once without the reference — rebuilding the `discord.File` from a fresh `io.BytesIO(image_data)`, since the failed attempt already consumed the first one. With `reply_to is None`, `HTTPException` propagates to the existing generic exception handler exactly as before this feature. `content`, an optional `str`, is sent as the image message's own text content (`None` — the default — is today's unchanged behavior); a quiet pipe segment uses it to surface a bare `🖌️` magic tell with no quote message to attach one to.

**`do_the_art` returns `pipe_chain.ArtResult`** (`message`, `image_bytes`, `size`, `elapsed`) on success, not a bare `True` — a `NamedTuple` (4-tuple) is always truthy, so every existing `if await do_the_art(...)` / return-ignoring call site is byte-for-byte unaffected; only the daily scheduler and the pipe-chain runner actually unpack it (both need `image_bytes` — the scheduler to retain the PNG, see Daily Image of the Day; the chain runner to feed it into the next segment's edit, see Pipes). `ArtResult` itself is defined in `pipe_chain.py`, not `bot_ross.py`, specifically so its truthiness guarantee is unit-testable despite `bot_ross.py` being unimportable under test (see `ArtResultTest` in `test_pipe_chain.py`). Both failure paths (over-limit, exception) still return `False`. `quiet=False` (the default, used by every existing top-level command) is unchanged behavior; `quiet=True` (used by the scheduler, request types `daily_image`/`daily_edit`, and by every pipe-chain edit segment, request type `pipe`) suppresses the "Generated in … | Monthly requests: …" trailer and swaps the exception-path message from `No painting for: {prompt}, exception for this request: {e}` to the prompt-free `No painting this time, exception for this request: {e}` — a quiet caller's prompt may carry a hidden magic mixin, and the normal failure line would spoil it. The over-limit message and the "Revised prompt" message are **not** gated by `quiet`.

To add a new image model: add an entry to `MODEL_CONFIGS` with its supported params and capability flags (including `supports_edit`).

## Key Dependencies

- `discord.py ~2.3.2` — bot framework
- `openai ~0.27.2` — legacy SDK (pre-1.0, uses `openai.ChatCompletion.create`)
- `aiohttp` — direct HTTP calls to the image generation endpoint
- `tzdata` — guarantees IANA timezone data for `zoneinfo` (used by `daily_schedule.py`/`BOT_TIMEZONE`) regardless of what the base image ships

## Notes

- The openai SDK usage is the legacy v0.27 API. If upgrading, `openai.ChatCompletion.create` must be migrated to the new client interface.
- gpt-image-2 does not return a `revised_prompt` field via the Image API (only the Responses API does).
- The `data/` directory must exist at runtime (Dockerfile creates it, including `data/daily_images/`; `bot_ross.py` also `os.makedirs(DAILY_IMAGES_DIR, exist_ok=True)` at startup since a bind-mounted `data/` volume masks the Dockerfile's `mkdir` — locally you may need to create both directories yourself).
